Internal tooling · Architecture & maintenance

Invoca Demo Generator

Turns a prospect's name and website into a complete, believable walkthrough of the Invoca platform — re-skinned entirely to that prospect's business, without touching production Invoca or waiting on anyone's access.

Live invoca-demo-platform.onrender.com Access Google sign-in, @invoca.com Deployed f9dfd49 58 demos saved

No engineering background needed. What the tool does, how it works, what it costs, what's shipped, and what could bite us. The second tab has the code-level detail for whoever maintains it.

01

What it is

An SE or Sales Rep types "Roto-Rooter" and its URL, waits a few minutes, and gets a working set of Invoca screens — dashboards, call transcripts, AI agent configuration, Signal management, Insights reports — where every number, campaign name, product category, agent script and conversion label reads as though it came from that prospect's own Invoca account.

It exists because building a credible demo used to mean one of two things: showing a generic sandbox that looked like nobody's business, or getting access to real customer data in the live platform. This tool needs neither. It is a self-contained replica, so anyone on the team can produce a prospect-specific demo in minutes without touching production Invoca and without waiting on anyone else. The shared library currently holds 58 saved demos.

02

How it fits together

Reading the diagram

There is one server, and it does three jobs. It checks who you are, it serves the website, and it is the only thing that talks to the paid AI services. Nothing sensitive ever sits in the browser — which matters, because the API keys we pay for live on that server and nowhere else.

Signing in. The tool is not public. Opening the URL hands you to Google to sign in, and it only lets you through if your email ends in @invoca.com. Google charges nothing for this.

Generating a demo — this is where the money goes. You give it a prospect name and website. The server then makes roughly 20 separate requests to Anthropic's Claude API for that one prospect: one quick call to settle the prospect's core vocabulary (does this business book "appointments", "consultations", "tours", "test drives"?), then 18 requests running in parallel, each writing one screen's worth of content — the marketing dashboard, the call transcripts, the AI agent's script, the Signal library, and so on. It also makes one call to Google Places for the prospect's real address and rating, and fetches their website once to grab a logo.

What costs money while you're demoing. Three features call Anthropic live: the AI agent you can text or talk to, the "Ask AI" panel that re-words any screen on the fly, and the transcript analyser. All three use Claude Haiku, the cheapest model, specifically because they run interactively. Separately, the voice agent's speech comes from Deepgram, the one integration billed per second of audio.

What this means for the spend

The bill scales with how many new prospects the team generates — not with how many demos they give. A finished prospect is saved permanently, so that cost is paid once per prospect, not once per demo; re-opening a saved demo later costs nothing at all.

Ten SEs re-using the 58 demos already in the library generate zero new Anthropic cost. The expensive model is used only during generation; everything interactive deliberately uses the cheap one.

04

What could bite us

Act on this first

The lock can fall off the door

Sign-in is only enforced while two settings are present. If either is cleared by accident, the tool keeps running — open to the public internet, with the whole demo library readable. It is correctly locked today; the risk is a future mistake.

No backup

All 58 demos live in one place

Saved demos sit on a single disk with no backup that I can find. If it were lost, they go with it. The ten built-in examples are stored with the code and would survive.

Single owner

One person knows how it works

The tool has had one author. The conventions are written down and the second tab is a real onboarding guide, but nothing is proven until a second person ships a change.

Data quality

A number that contradicts itself

Every generated prospect claims 26 unmet call signals but lists only a handful. A prospect who counts would notice. The fix is in flight; existing demos keep the old numbers until regenerated.

Unreleased work

The Signal rebuild isn't saved

Five screens exist only on one laptop, not committed to the repository. An accident loses them.

Speed ceiling

~2m45s per prospect is structural

That's set by how many AI requests run at once, not by any one slow step. Going faster means more simultaneous requests. Worth knowing before anyone promises "instant".

Full detail on all nine risks, including the four sample prospects that need regenerating, is in the technical tab.

Two corrections to the brief for this document

1. There is no ChatGPT/OpenAI integration, and no OpenAI spend. A grep for openai, api.openai.com, gpt-4 and chat.completions across src/, engine/, server.ts and package.json returns nothing. The "ChatGPT tile" is src/screens/ChatGptAd.tsx — a pixel-replica of chatgpt.com rebuilt from a saved page capture, showing the prospect as a sponsored result, driven entirely by the local profile plus Mapbox tiles.

2. Deepgram appears to be working, not blocked. The live service reports "ttsProvider":"deepgram","ttsKey":true, so a key is set in the Render environment and the path is wired end to end (engine/tts.ts → POST /api/tts → src/components/VoiceCall.tsx). If the voice agent is blocked, the blocker is not a missing key.

Authentication — what it actually is

The brief calls this "SSO"; the code implements Google OAuth 2.0 with a domain allowlist. Not the same as Okta/SAML SSO, and worth stating precisely to a security-minded audience.

From googleAuth.ts: a standard OAuth 2.0 authorization-code flow written against Node's built-in crypto and fetch with no extra dependencies. Scope openid email profile, a CSRF state cookie, and on success a signed HttpOnly session cookie. Access requires the email domain to match ALLOWED_EMAIL_DOMAIN (default invoca.com). The gate turns on only when both GOOGLE_CLIENT_ID and GOOGLE_CLIENT_SECRET are set — so a misconfigured deploy fails open. See risk 1.

/healthz, /api/status and /api/canary are registered before the gate and are public by design — counts, booleans and timings only, never prospect names, demo IDs, emails or key values (server.ts:62–88).

02

Core flows

Generating a new prospect

Entry point: src/screens/Launch.tsx — name + website URL.

  1. Browser — Launch.tsx:310 posts { name, url } to POST /api/generate.
  2. Server — server.ts:109 requires ANTHROPIC_API_KEY, calls generateProfile() (engine/core.ts:994).
  3. Vocabulary first — generateTerms() (core.ts:339), one fast Haiku call, fixes the canonical terms: bookingTerm, customerNoun, plus qualified-call and conversion terms. Everything downstream reuses these, which is what stops one screen saying "Appointment" while another says "Consultation".
  4. Numbers second — buildScale() / scaleRules() pin every canonical figure before content generation, so the 18 phases cannot disagree about call volume or revenue.
  5. 18 phases in parallel — runPool(tasks, CONCURRENCY = 6) (core.ts:220, called at core.ts:1056), ordered longest-processing-time-first so a heavy phase never starts late. Phases: dashboardChannels, dashboardSegments, opsDashboard, callReview, agentConfig, signalManager, dashboard, digitalInsights, conversationIntelligence, callDetail, aiAgentConversion, voiceConversationIntelligence, smsConversationIntelligence, aiMessagingImpact, voiceRoutingDemo, screenpops, and two more.
  6. Enrichment — engine/places.ts for the real location, engine/ogImage.ts for the logo.
  7. Validation — parsed against src/data/schema.ts. A malformed phase fails here, not on screen.
  8. Persistence — src/data/generated/<slug>.json (server.ts:128) and, via the library, the Render disk.

Cost: ~20 Anthropic calls per prospect, once. Steps 3–5 are the entire AI spend of a generation.

The bundled examples

Ten seeds ship in the repo at src/data/generated/*.json and load with zero API calls: autonation, continuing-life, goosehead-insurance, key-whitman-eye-center, mattress-firm, national-van-lines, orlando-health, roto-rooter-plumbing-and-water-cleanup, surfside-healthcare, vector-security. An eleventh, Shady Blinds, is hand-authored TypeScript (src/data/profiles/shadyBlinds.ts) and is the reference implementation — when a screen is built, it is built against Shady Blinds first.

Launch.tsx:155 separates samples (bundled, owned by nobody) from library demos (owned by their creator). The active prospect lives in src/data/ProfileContext.tsx, mirrored to localStorage under invoca-demo:activeId. ⚠ The provider reads that key on mount only — switching prospects needs a full reload, which is easy to get wrong when testing.

Vector Security shows per-prospect tuning: commits 2773cec and d083a30 renamed its Google Ads keyword to a search-like phrase and its Digital Insights signal to "Quote Discussed", because an alarm company quotes rather than books.

Writes go through a single canWrite() check (demoApi.ts:65) so PATCH and DELETE can never diverge in who they let through. The frontend lock is convenience only; the server enforces it.

Storage — one JSON file per demo at DATA_DIR/demos/<id>.json, written atomically (temp file then rename, demoStore.ts:88). DATA_DIR resolves $DATA_DIR → /data (the mounted Render disk) → a local fallback (demoStore.ts:24–40). Live service confirms storage.persistent: true.

In-demo editing ("Ask AI") — the top-bar sparkle opens a drawer that edits the current screen's data via POST /api/ai-assistant (server.ts:154 → engine/assistant.ts). Edits are keyed ${profileId}::${pathname} in src/data/AiAssistantContext.tsx, so an edit on one screen cannot leak to another. src/data/editGuard.ts rejects structural changes while allowing content changes; engine/demoPatches.ts applies the result. Re-opening replays saved customizations over the base profile.

03

Maintenance guide

For a second SE joining to help maintain this.

Local setup

git clone git@github.com:ddesai-invoca/invoca-demo-platform.git
cd invoca-demo-platform
npm install
# create .env (see below) — at minimum ANTHROPIC_API_KEY
npm run dev            # localhost:5173 — Vite serves the UI AND dev /api/* routes

vite.config.ts mounts dev copies of /api/generate, /api/delete-profile, /api/chat, /api/place and the demo library, so local dev behaves like production. To exercise the production server path: npm run serve.

Environment variables

Server-side only. Never prefix a secret with VITE_ — that puts the value in the browser bundle. VITE_MAPBOX_TOKEN is the sole intentional exception (a public map-tile token).

.env is git-ignored. Confirm before every commit that it has not been staged.

Deploying

Render auto-deploys on push to main. There is no render.yaml — the service is configured in Render's dashboard (inferred from the file's absence plus the RENDER_* env vars read in engine/status.ts; verify in the Render UI). 

npm run build                                             # must pass
./node_modules/.bin/tsc --noEmit -p tsconfig.app.json     # both configs
./node_modules/.bin/tsc --noEmit -p tsconfig.node.json
git push origin main                                      # triggers the deploy

Confirm the deploy by checking the commit SHA, not that the site responds:

curl -s https://invoca-demo-platform.onrender.com/api/status

The old instance keeps answering 200 during a rollout, so an HTTP-status check reports success while the previous build is still live. Compare commitShort against what you pushed. (This bit me twice — both times the check "passed" against the old build.)

Adding a screen or a vertical

  • A new screen: ask which live Invoca URL to replicate, save a SingleFile capture, build from measured values. Screens in src/screens/, styles in src/styles/app.css under a per-screen class prefix.
  • A new vertical: nothing to add. Generation is prompt-driven and vertical-agnostic — the reskin() directive in engine/core.ts re-skins every label from the prospect's brief. A vertical needs code only when it needs a screen that does not exist yet.
  • The rule that matters most: a change for one screen must not alter any other. Shared components take opt-in props defaulted to current behaviour, CSS is scoped per screen, and you verify by loading another screen and asserting the old values. Documented in CLAUDE.md under Conventions.

Common failure points

  1. tsc / tsx "not found" — wrong directory. cd to the repo root first.
  2. An engine prompt edit does nothing — engine modules are dynamically imported and Node-cached. Restart the dev server. (The CLI is a fresh process and doesn't need it.)
  3. Run both typecheck configs — a change can pass the app config and break the node one.
  4. Deploy verification — check the SHA, not the status code.
  5. Switching prospects while testing — ProfileContext reads the active id on mount, so a pushState navigation keeps the old profile. Reload.
  6. Nightly canary — engine/canary.ts generates a throwaway prospect at ~5am ET, checks it against a time budget and data-quality rules, deletes it, and publishes the result at GET /api/canary. missing/stale mean no result, which is deliberately not reported as healthy.
04

Open questions & risks

  1. The sign-in gate fails open. The gate is active only when both GOOGLE_CLIENT_ID and GOOGLE_CLIENT_SECRET are present (googleAuth.ts, DEPLOY.md). If either is cleared or mistyped in Render, the app keeps serving — unauthenticated, to the public internet, with the whole demo library readable. It reports authGate: true today, so this is a latent misconfiguration risk, not a present exposure. Should fail closed.
  2. The Signal rebuild is uncommitted. Five screens' worth of work (four new screens plus a nav change and a 158 KB image asset) exists only in the working tree. An accidental git checkout loses it.
  3. Generated profiles carry a known data inconsistency. Every engine-generated prospect writes signalsUnmet: 26 and signalsNa: 25 while listing only 5–15 signal names, so the badge contradicts the list it expands — and the identical 26/25 across all ten profiles is itself a giveaway. The new Insights call page counts the list instead; the older src/screens/CallDetail.tsx still shows the declared number. The 58 demos already saved keep the bad values until regenerated.
  4. Phrase data in the Semantic Signal Library is uneven, and the file says so. Only one template drawer was open in the source capture, so Ask for Appointment has all 44 real phrases, two more have partial lists from screenshots, and the other 12 templates' phrases were authored rather than captured. Each entry carries a captured: true/false flag (src/data/semanticSignals.ts). Low risk — generic conversational phrases, not customer data — but they are not Invoca's official library content.
  5. Four sample prospects violate a rule we otherwise enforce. The "volume is not value" story (the highest-volume row must show the worst conversion rate) is enforced in prompts and checked by the canary, but continuing-life, key-whitman-eye-center, orlando-health and mattress-firm predate the fix and still read inverted. They need regenerating.
  6. The generation floor is structural. ~2m45s per prospect is set by CONCURRENCY = 6 against 18 phases, not by any single slow call. Faster means raising concurrency (more simultaneous Anthropic requests, i.e. rate-limit exposure) or cutting phases.
  7. Single point of failure on one person's knowledge. The conventions that keep this maintainable — measure from captures, derive rather than invent, one screen's change stays in its screen — are in CLAUDE.md, but the tool has had one author. This guide is the mitigation; a second maintainer shipping a screen is the test of it.
  8. Deployment config lives only in Render's dashboard. With no render.yaml, the service definition is not version-controlled and cannot be recreated from the code alone. (Inferred from the file's absence — verify in the Render UI.)
  9. Demo storage is a mounted disk, not a database. One JSON file per demo on Render's persistent disk. Writes are atomic and it reports persistent: true, but there is no evidence in the repo of a backup. If the disk were lost, all 58 saved demos go with it. The ten bundled samples live in git and would survive.

Internal tooling · Architecture & maintenance

Invoca Demo Generator

Turns a prospect's name and website into a complete, believable walkthrough of the Invoca platform, re-skinned entirely to that prospect's business, without touching production Invoca or waiting on anyone's access.

01

What it is

An SE or Sales Rep types "Roto-Rooter" and its URL, waits a few minutes, and gets a working set of Invoca screens: dashboards, call transcripts, AI agent configuration, Signal management, Insights reports. Every number, campaign name, product category, agent script and conversion label reads as though it came from that prospect's own Invoca account.

It exists because building a credible demo used to mean one of two things: showing a generic sandbox that looked like nobody's business, or getting access to real customer data in the live platform. This tool needs neither. It is a self-contained replica, so anyone on the team can produce a prospect-specific demo in minutes without touching production Invoca and without waiting on anyone else. Finished demos are saved to a shared library the whole team can open, and re-opening one is instant.

Minutes, not days

A prospect-ready demo on demand

Name and website in, a full platform walkthrough out. No scheduling, no sandbox request, no waiting on another team.

Their business, not ours

Every label speaks the prospect's language

A dealership books test drives, a health system books consultations, an alarm company quotes. The screens follow, down to the agent's script.

Zero production risk

Nothing touches the real platform

It is a replica with its own data. No customer account is opened, and no production Invoca system is involved at any point.

Reusable

Built once, shared with the team

Finished demos are saved to a shared library the whole team can open, so the work compounds instead of being rebuilt for each call.

02

How it fits together

Reading the diagram

There is one service, and it does three jobs. It checks who you are, it serves the screens, and it is the only thing that talks to the outside services. The keys for those services live on that server and nowhere else, so nothing sensitive ever reaches the browser.

Signing in. The tool is not public. Opening the URL hands you to Google to sign in, and it only lets you through if your email ends in @invoca.com.

Generating a demo. You give it a prospect name and website. The server makes one quick request to settle the prospect's core vocabulary (does this business book "appointments", "consultations", "tours", or "test drives"?), then 18 requests running in parallel, each writing one screen's worth of content: the marketing dashboard, the call transcripts, the AI agent's script, the Signal library, and so on. It also looks up the prospect's real address and rating, and reads their homepage once to pick up a logo. The whole thing takes about two and a half minutes.

Why it stays consistent. The vocabulary and the headline numbers are settled before those 18 requests start, and every one of them is handed the same set. That is what stops one screen saying "Appointment" while another says "Consultation", or two dashboards disagreeing about call volume.

Once it exists, it is reusable. A finished prospect is saved permanently to the shared library, so re-opening it later is instant and available to the whole team, not just the person who built it.

Authentication: what it actually is

This is Google OAuth 2.0 with a domain allowlist, not Okta/SAML SSO. Worth stating precisely, because the two are often used interchangeably.

From googleAuth.ts: a standard OAuth 2.0 authorization-code flow written against Node's built-in crypto and fetch with no extra dependencies. Scope openid email profile, a CSRF state cookie, and on success a signed HttpOnly session cookie. Access requires the email domain to match ALLOWED_EMAIL_DOMAIN, which defaults to invoca.com.

/healthz, /api/status and /api/canary are registered before the gate and are public by design: counts, booleans and timings only, never prospect names, demo ids, emails or key values (server.ts:62–88). That is what lets the nightly self-check report in without being handed a credential.

02

Core flows

Generating a new prospect

Entry point: src/screens/Launch.tsx, name + website URL.

  1. Browser: Launch.tsx:310 posts { name, url } to POST /api/generate, which answers with an SSE progress stream.
  2. Server: server.ts:109 requires ANTHROPIC_API_KEY, calls generateProfile() (engine/core.ts:994).
  3. Vocabulary first: generateTerms() (core.ts:339), one fast Haiku call, fixes the canonical terms bookingTerm and customerNoun plus the qualified-call and conversion terms. Everything downstream reuses these, which is what stops one screen saying "Appointment" while another says "Consultation".
  4. Numbers second: buildScale() / scaleRules() pin every canonical figure before content generation, so the 18 phases cannot disagree about call volume or revenue.
  5. 18 phases in parallel: runPool(tasks, CONCURRENCY = 6) (core.ts:220, called at core.ts:1056), ordered longest-processing-time-first so a heavy phase never starts late.
  6. Enrichment: engine/places.ts for the real storefront photo, rating and address used by the ChatGPT placement, engine/ogImage.ts for the logo.
  7. Validation: parsed against src/data/schema.ts. A malformed phase fails here, not on screen.
  8. Persistence: src/data/generated/<slug>.json (server.ts:128) and, via the library, the Render disk.

The ~2m45s floor is structural

It is set by how many requests run at once, not by any single slow step, so the way to go faster is more concurrency rather than optimising a phase. Worth knowing before anyone promises "instant".

The bundled examples

Ten seeds ship in the repo at src/data/generated/*.json and load with zero API calls: autonation, continuing-life, goosehead-insurance, key-whitman-eye-center, mattress-firm, national-van-lines, orlando-health, roto-rooter-plumbing-and-water-cleanup, surfside-healthcare, vector-security. An eleventh, Shady Blinds, is hand-authored TypeScript (src/data/profiles/shadyBlinds.ts) and is the reference implementation: when a screen is built, it is built against Shady Blinds first.

Launch.tsx:155 separates samples (bundled, owned by nobody) from library demos (owned by their creator). The active prospect lives in src/data/ProfileContext.tsx, mirrored to localStorage under invoca-demo:activeId. ⚠ The provider reads that key on mount only, so switching prospects needs a full reload. This is easy to get wrong when testing, and it invalidates any test that swaps the id and then navigates with pushState.

Vector Security shows per-prospect tuning: commits 2773cec and d083a30 renamed its Google Ads keyword to a search-like phrase and its Digital Insights signal to "Quote Discussed", because an alarm company quotes rather than books.

Writes go through a single canWrite() check (demoApi.ts:65) so PATCH and DELETE can never diverge in who they let through. The frontend lock is convenience only; the server is what enforces it.

Storage: one JSON file per demo at DATA_DIR/demos/<id>.json, written atomically (temp file then rename, demoStore.ts:88). DATA_DIR resolves $DATA_DIR then /data (the mounted Render disk) then a local fallback (demoStore.ts:24–40).

In-demo editing ("Ask AI"): the top-bar sparkle opens a drawer that edits the current screen's data via POST /api/ai-assistant (server.ts:154 to engine/assistant.ts). Edits are keyed ${profileId}::${pathname} in src/data/AiAssistantContext.tsx, so an edit on one screen cannot leak to another. src/data/editGuard.ts rejects structural changes while allowing content changes, and engine/demoPatches.ts applies the result. Re-opening a demo replays its saved customizations over the base profile.

Maintenance guide

For a second SE joining to help maintain this.

Local setup

git clone git@github.com:ddesai-invoca/invoca-demo-platform.git
cd invoca-demo-platform
npm install
# create .env (see below) - at minimum ANTHROPIC_API_KEY
npm run dev            # localhost:5173 - Vite serves the UI AND dev /api/* routes

vite.config.ts mounts dev copies of /api/generate, /api/delete-profile, /api/chat, /api/place and the demo library, so local dev behaves like production. To exercise the production server path, use npm run serve.

Server-side only. Never prefix a secret with VITE_, which would put the value in the browser bundle. VITE_MAPBOX_TOKEN is the sole intentional exception, being a public map-tile token.

.env is git-ignored. Confirm before every commit that it has not been staged.

Deploying

Render auto-deploys on push to main. There is no render.yaml; the service is configured in Render's dashboard (inferred from the file's absence plus the RENDER_* env vars read in engine/status.ts; verify in the Render UI). 

npm run build                                             # must pass
./node_modules/.bin/tsc --noEmit -p tsconfig.app.json     # both configs
./node_modules/.bin/tsc --noEmit -p tsconfig.node.json
git push origin main                                      # triggers the deploy

Confirm the deploy by checking the commit SHA, not that the site responds:

curl -s https://invoca-demo-platform.onrender.com/api/status

The old instance keeps answering 200 during a rollout, so an HTTP-status check reports success while the previous build is still live. Compare commitShort against what you pushed.

Adding a screen or a vertical

  • A new screen: ask which live Invoca URL to replicate, save a SingleFile capture, and build from measured values. Screens go in src/screens/, styles in src/styles/app.css under a per-screen class prefix.
  • A new vertical: nothing to add. Generation is prompt-driven and vertical-agnostic, and the reskin() directive in engine/core.ts re-skins every label from the prospect's brief. A vertical needs code only when it needs a screen that does not exist yet.
  • The rule that matters most: a change for one screen must not alter any other. Shared components take opt-in props defaulted to current behaviour, CSS is scoped per screen, and you verify by loading another screen and asserting the old values still render. Documented in CLAUDE.md under Conventions.

Common failure points

  1. tsc / tsx "not found": wrong directory. cd to the repo root first.
  2. An engine prompt edit does nothing: engine modules are dynamically imported and Node-cached. Restart the dev server. The CLI is a fresh process and does not need it.
  3. Run both typecheck configs: a change can pass the app config and break the node one.
  4. Deploy verification: check the SHA, not the status code.
  5. Switching prospects while testing: ProfileContext reads the active id on mount, so a pushState navigation keeps the old profile. Reload.
  6. Nightly canary: engine/canary.ts generates a throwaway prospect at ~5am ET, checks it against a time budget and data-quality rules, deletes it, and publishes the result at GET /api/canary. missing and stale mean no result, which is deliberately not reported as healthy.
  7. Editing a live demo: pull the demo JSON locally, edit, then PATCH it back. A stale localStorage cache can mask the change in the browser.
04

Known limitations

Data quality

A signal count that contradicts its own list

Every engine-generated prospect writes a fixed signalsUnmet / signalsNa pair while listing only a handful of signal names, so the badge disagrees with the list it expands. The newer Insights call page counts the list instead. A fix is in flight; existing demos keep the old numbers until regenerated.

Content

Four sample prospects need regenerating

continuing-life, key-whitman-eye-center, orlando-health and mattress-firm carry an inverted outcome story from before that rule was enforced in the engine.

Throughput

The ~2m45s generation floor

Structural, set by concurrency rather than by any one slow phase. Raising it means running more phases at once, which trades against rate limits.

Coverage

Two Signal builders are not built

Signal AI Studio and the rule-based builder route to placeholders. The five Signal screens that do exist are built and working but not yet released.

Ownership

One author so far

The conventions are written down in CLAUDE.md and this tab is a real onboarding guide, but none of it is proven until a second person ships a change through it.

Rendering

ThoughtSpot screens do not serialise

Insights & Analytics is embedded ThoughtSpot, rendered at runtime, so a SingleFile capture of it comes back empty. Those screens are restyled from the --ts-var-* tokens instead.

Nothing here was built from scratch. The tool is assembled out of standard, off-the-shelf services, each doing one job. That is what let it go from an idea to something the team uses without a platform team, a data centre, or a procurement cycle.

What the demo uses to run

Each of these does one specific job inside a demo. They are all standard services with published, documented interfaces, so none of them required anything custom to be built.

The content

Anthropic API (Claude)

Writes the whole prospect: dashboards, transcripts, campaign names, the agent's script. It also powers the in-demo "Ask AI" panel, which re-words any screen on the spot.

The voice

Deepgram and ElevenLabs

Give the prospect's AI agent a speaking voice, so you can hold a real conversation with it on a call rather than only exchanging text.

The front door

Google sign-in

Restricts the tool to @invoca.com accounts. Anyone outside Invoca who opens the link is turned away at sign-in.

The real details

Google Places

Supplies the prospect's genuine storefront photo, star rating and address, which is what makes the generated ChatGPT ad screen look like the real listing.

The maps

Mapbox

Draws any map that appears in a demo, including the location shown alongside the prospect in the ChatGPT placement.

Why it matters

Everything is replaceable

Each service is reached through a small, isolated piece of code. Swapping one out, as already happens between the two voice providers, is a contained change.
